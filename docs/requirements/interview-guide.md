# ChangeScope 半结构化访谈提纲

**访谈对象：** 有 GitHub 团队开发、PR 审查或项目管理经验的真实人员。
**时长：** 每人10–20分钟；问题不必逐字机械朗读。

## 开场和许可

“我们在做一个用于辅助 GitHub 代码审查的课程项目，希望了解你实际工作/课程项目中的流程和困难。我们只记录匿名化的摘要，公开引用前征得你的同意。你可以跳过不愿回答的问题。”

## 核心问题（开放性）

1. 请介绍你最近一次在 GitHub 提交或审查 Pull Request 的真实经历。
2. 当时你是怎样判断这次修改风险高不高的？能举一个具体例子吗？
3. 有没有发生过只修改了一个文件，却遗漏另一处相关逻辑的情况？是怎样发现的？
4. 你通常如何检查修改涉及的相关文件？现有 GitHub 页面有什么帮助或不足？
5. 团队是如何决定由谁 Review 的？是否出现过一人任务过重、其他人不熟悉代码的情况？
6. 对于陌生模块，你最需要哪些证据才能更有把握地审查？
7. 如果系统显示“某文件在历史上经常与本次修改文件一起变更”，你会怎样验证这个提示？
8. 你能接受自动计算的风险评分吗？哪些解释或证据会让它更可信？
9. 你需要怎样的反馈/纠错机制？哪些提醒会让你觉得是噪声？
10. 你对 GitHub 授权、私有仓库访问、响应速度或服务故障有什么顾虑？
11. 我们目前设想的功能里，哪一个你认为没价值或不应该做？为什么？
12. 最后，有没有我们没问到、但你认为对代码审查很重要的事情？

## 按角色追问

- **开发者：** 提交前自查、误报、改动版本间风险变化。
- **审查者：** 重点排序、关联证据、检查结果反馈。
- **技术负责人/质量管理员：** 权重策略、人员权限、负载平衡、效果度量。
- **维护者：** API 配额、缓存和故障恢复、私密数据边界。

## 记录方式

把“事实原话/例子”“访谈人理解”“候选需求”分开记录。访谈后将实际记录复制到 `interview-records/I01.md` 等，并将故事关联到具体记录小节。
