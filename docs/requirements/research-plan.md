# ChangeScope 需求调研计划（执行版）

> 文档状态：可执行计划，尚未代表完成调研。
> 调研开始日期：TODO；课程第3课开课前一天24:00前需完成故事 Issue 检查点。

## 一、调研目标

1. 弄清实际 GitHub 用户如何识别 PR 审查风险与潜在关联文件。
2. 确认审查员选择和负载分配是否存在可重复的痛点。
3. 判断用户是否需要可解释的风险提示、可验证的关联证据与有效性反馈。
4. 识别仓库授权、数据保密、性能、故障恢复等非功能要求。
5. 找到**不支持**项目原先设想的证据，允许删改或合并候选功能。

## 二、拟访谈干系人

| 类型 | 目标数量（建议，非已完成） | 访问重点 | 负责联系 |
| --- | --- | --- | --- |
| 有 GitHub PR 使用经验的开发者 | 2位 | 提交 PR 前的风险判断、遗漏影响 | B |
| 有 Review / Approve 经验的审查人员 | 1–2位 | 审查优先级、审查证据、推荐适用性 | C |
| 团队技术负责人/质量协同角色 | 1位（可由兼任者提供视角） | 分派与策略、指标、授权限制 | A / D |
| GitHub 仓库维护者（如可找到） | 选访 | 数据权限、故障恢复、API 访问 | D |

建议4–6次有效访谈；样本量属于小规模课程探索，不足以代表整个软件行业。如找不到真实质量管理员，应在报告中如实标注角色视角缺口。

## 三、访谈安排

- 第1步（立即）：完成分工、确定受访者、说明用途、征得记录许可。
- 第2步：每次访谈约10–20分钟，用开放性问题追问最近一次真实经历。
- 第3步：记录匿名编号（I01/I02…）、角色、经验、原话摘要、具体例子及反对意见。
- 第4步：对观点标注其证据来源；不要用“大家都认为”代替样本数。
- 第5步：4人会议审查候选需求：接受 / 修改 / 拒绝 / 待验证。
- 第6步：调研报告经 GitHub PR 评审后合并，再创建/完善故事 Issues。

## 四、方法

主方法：半结构化访谈。辅方法：公开 GitHub 项目的审查流程观察、竞品对比。公开资料可以支持背景研究，不能替代真人访谈证据。

## 五、质量与隐私

- 保留实际访问日期、记录人和真实证据；引述需受访者同意。
- 公开仓库只放脱敏摘要或经授权公开的材料，原始录音/联系人信息私下保管。
- 不得假造人数、访谈语句、问卷结果、截图、使用数据。
- 不收集或上传 GitHub OAuth token、密码、私有仓库源代码。
- 记录反例：用户不需要某项功能、审查流程实际上更简单等。

## 六、调研产出

- 访谈记录：`interview-records/I01.md`、`I02.md` 等（真实访谈后新建）
- 调研报告：`research-report.md`
- 候选故事：`issue-drafts/`
- 需求追踪索引：`user-stories-index.md`
- GitHub：每条故事单独 Issue，`story` 标签 + Assignee + 证据链接
