# ChangeScope 项目发起人需求陈述与原始依据

> 记录类型：**项目立项讨论纪要（有真实原话）**，不是独立开发人员访谈。  
> 文档状态：**已根据前期实际聊天内容整理，待小组核对和归档原始记录**。  
> 整理日期：2026-11-26（整理日期不等于发言日期）。  
> 证据对象：参与项目选题讨论的本组成员；不能据此推定其他开发人员具有相同需求。  
> 原始材料：先前的选题聊天记录。请由当事人按课程和隐私要求自行导出或截图归档；当前 GitHub 文件中**尚无可核验原始聊天截图链接**。

## 一、讨论背景

本组最初希望选择一个软件工程课程设计项目。普通校园业务系统被认为缺少新颖性，之后将选题范围调整为软件工程工具，并重点考虑技术深度、8周内的可实施性、课程对多角色的要求，以及与 GitHub 已有功能的重叠问题。经过多轮讨论，形成了 ChangeScope（Git历史挖掘与PR风险分析）这一项目方向。

此段为**对选题讨论的归纳**，不是一位外部代码审查员对真实审查问题的陈述。

## 二、可溯源的原始表达

下表“原话”一栏直接摘录了项目选题时用户确实发送过的消息；**不增加虚构采访日期、受访者身份、采访人数或实际工作经历**。

| 编号 | 选题讨论中的真实原话 | 可支持的结论 | 不能据此证明 |
|---|---|---|---|
| INIT-01 | “不够新颖，太多人做了” | 发起人重视项目相对常见课程题目的差异化 | 代码审查员实际面临哪些具体痛点 |
| INIT-02 | “继续推荐软件工程工具类选题，要求新颖、有技术深度、8周内可实现。” | 发起人明确选定软件工程工具方向，要求技术深度与周期可行性 | 所有目标用户都会选择该技术路线 |
| INIT-03 | “课程项目要求至少有三个角色，01选题有吗” | 系统规划必须回应课程对不少于三类角色的约束 | 这三个角色已经过真实用户验证 |
| INIT-04 | “这些功能github本身有吗？有没有重复的地方” | 发起人重视与 GitHub 原生功能的区分，不希望重复建设 | GitHub 功能对比已经完成实测，或工具价值已经获证 |
| INIT-05 | “那你帮我重新构思” | 发起人认为前一版方案需要重新设计 | 前一版被真实用户访谈否决 |

**证据类型判定：** INIT-01—INIT-05 是真实项目发起人需求陈述，适合放在“选题动机和立项依据”章节；它们**不是**关于 PR 审查痛点的真人外部用户访谈证据。

## 三、可提炼的立项需求

| 编号 | 需求依据 | 对项目方案的约束或影响 | 对应设计选择 |
|---|---|---|---|
| DR-01 | INIT-01、INIT-02 | 与常见 CRUD 类课程项目区分，并具有可解释的技术核心 | 以 Git 历史关联挖掘与风险评估为核心 |
| DR-02 | INIT-02 | 核心范围要适合8周课程周期、支持阶段性交付 | 分成历史挖掘、PR风险评估、决策支持三个增量 |
| DR-03 | INIT-03 | 至少设计三个有不同目标的业务角色 | 开发人员、代码审查员、质量管理员 |
| DR-04 | INIT-04、INIT-05 | 避免重新实现 GitHub 已有的 PR 审批和评论流程 | 只做独立分析与建议，审批、合并仍在 GitHub |

以上是**设计决策与原话的关联**，不表示相关功能已经开发完成或经过目标用户验证。

## 五、建议在GitHub中保存的证据链

1. 当事人自行导出与上述原话对应的原始聊天截图或文字记录，检查并移除隐私信息。
2. 经当事人同意，放在仓库例如 `docs/requirements/evidence/project-origin/` 或记录可访问的证据链接。
3. 在调研报告中引用 `INIT-01` 等编号，并指向原始记录的具体部分。
4. 另行开展真实开发人员/代码审查员访谈，在 `docs/requirements/evidence/interviews/` 记录匿名化的真人访谈纪要。
5. 只有真实访谈与评审支持的产品需求才能升级为“已确认”，否则保留“待验证”。

## 六、课堂上如何准确介绍这份材料

这份材料能回答：**“为什么我们选这个项目，为什么不直接重复GitHub？”**

它还不能回答：**“你们真实访谈了多少位开发者、他们具体提出哪些业务痛点？”**

对于第二个问题，如尚未完成访谈，应如实说明正处于需求假设验证阶段，不能编造受访人数、原话或访谈结论。
