# ChangeScope 需求调研阶段报告（初稿：项目动机与待验证假设）

**状态：阶段性初稿。已新增对先前同学非正式口头交流的事后回忆纪要，但未保存当场笔录、具体人数或独立确认；仍需复核，且尚未完成正式需求基线评审。**

## 1. 调研目标

本阶段拟解决三个问题：①项目选题为什么具有独立价值；②目标用户在PR代码审查过程中是否真正需要历史关联、风险解释、审查员推荐；③哪些需求能转化为可检验的用例和验收标准。

## 3. 初步发现：项目发起人明确表达的需求

### 发现F1：项目需要体现差异化
原话 INIT-01：“不够新颖，太多人做了”。

**解释：** 发起人不希望重复常见课程项目，团队因此转向有独立分析能力的软件工程工具。这个结论仅用于说明选题理由。

### 发现F2：必须平衡深度与交付可行性
原话 INIT-02：“继续推荐软件工程工具类选题，要求新颖、有技术深度、8周内可实现。”

**解释：** 提案应突出明确的技术核心，同时控制范围：先完成历史文件共变更，再完成PR风险评估，最后支持审查决策和反馈；这是范围安排的依据，不是实际交付进度。

### 发现F3：需求模型要能覆盖多角色
原话 INIT-03：“课程项目要求至少有三个角色，01选题有吗”。

**解释：** 方案规划了开发人员、代码审查员和质量管理员三个业务角色，后续需要通过访谈确认分工是否贴近真实团队。

### 发现F4：必须明确和GitHub的边界
原话 INIT-04：“这些功能github本身有吗？有没有重复的地方”。

**解释：** 项目应聚焦Git历史挖掘、关联分析、可解释风险提示、推荐与反馈；GitHub自身负责PR评论、审批和合并。该分工是设计意图，不能代替已完成的竞品实测结论。

## 3A. 新补充的真实交流线索（需复核）

除了早期的选题讨论，组员现在回忆起此前曾与**不少同学**聊过 GitHub 团队协作。按组员当前复述，同学们觉得 PR 难度较大，特别是**许多组员一起提交 PR 时，合并与检查过程比较麻烦**。

这是**事后回忆概述**，不是当场记录，也没有统计受访人数。我们将其记录为 `OR-01/OR-02`，并保留关键歧义：“合并起来检查”究竟是指**合并冲突**还是**多份 PR 的差异审查/影响范围核查**。两者需求不同，不能直接等同于“历史关联文件遗漏”。

由此可以初步提出的**问题需求**是：`多人协作场景下，开发者或审查员需要更清楚地了解PR变更与检查重点，以便减少审查和整合时的认知负担`。它只是一种候选概括，尚需受访同学确认其准确性。将此作为FR-05、FR-07等候选需求的**部分动机**是合理的，但它不能直接证明风险评分、关联挖掘或审查员推荐有用。

- 核对模板：[发给此前交流同学的确认消息](05_发给同学的核对消息.md)

## 3B. 两类困难的区别与范围决策（补充澄清）

项目组成员2026-11-26明确补充：此前同学讨论中**合并冲突与PR审查繁琐都有提到**。该信息仍属事后回忆，已写入 `04_非正式交流回忆纪要_待核对.md`，并非受访者当场记录。

| 两类困难 | 用户面临的实际情境 | ChangeScope拟议应对 | 本期是否实现 | 证据与局限 |
|---|---|---|---|---|
| 合并冲突 | 分支内容相互冲突，合并需人工处理 | 可选：显示GitHub返回的PR可合并状态与冲突提示、跳转原生解决界面 | **不作为核心必做；待确认的扩展需求** | 不自动合并、不自动修改冲突代码；需验证是否真的有价值 |
| PR审查繁琐 | 并行PR多、需阅读差异和理解潜在影响 | 核心：PR风险概览、历史关联文件与提交依据、审查建议 | **核心需求假设** | 仍需核查是否真正减少遗漏或时间；不能断言已有效 |

**项目定位：** “面向多人GitHub协作的PR审查风险与变更影响分析工具，提供有限的合并状态提示（可选），但不承担合并冲突自动解决”。这同时回应两种真实回忆，又保持8周项目范围可控。

## 7. 阶段性结论

本组对**项目选题的初衷、范围和约束**已经有真实的讨论线索，可以据此解释选择ChangeScope而非一般管理系统的理由。根据该方向，已形成可供讨论的SRS、用例图、详细用例和需求追溯矩阵候选稿。

通过事后回忆可以辨认出“多人PR合并和检查繁琐”的**初步反馈方向**，但尚无当场记录与受访者核对，**已由项目组成员澄清包含两种困难，但尚不能证明各自发生频率、具体案例，也不能证明ChangeScope比已有工具更有效**。下一步是完成至少覆盖开发、审查和维护视角的真人访谈，检验业务假设后修订需求；再经真实组员评审、PR合并和Release发布需求基线。
