## 1. 交流背景和已知事实

根据组员的回忆，项目组选题和讨论过程中曾经向**不少同学**了解过 GitHub 团队协作、Pull Request（PR）方面的困难。当时的交流较为随意，没有安排正式访谈，也没有同步记录问题、回答、人数或时间。

此前能够回忆的**交流内容总结**是：

> 同学们普遍觉得 PR 难度比较大，尤其是很多组员一起 PR 的时候，合并起来检查很麻烦。

**2026-11-26 追加澄清（项目组成员本人补充）：** 此前讨论中的困难**同时包括两种情况**：

- **合并冲突：** 多个组员修改代码后，Git 分支合并时可能出现冲突，需要人工定位和处理。
- **PR审查繁琐：** 多个组员提交PR时，审查员需要阅读多份修改、理解潜在影响并协调检查，工作量较大。

这是一名项目组成员对**既往同学交流内容的事后回忆和分类澄清**，不是重新访谈的结果。不能将这两项归为已量化的痛点，也不能据此推定所有受访者都同时遭遇这两种困难。

**说明：** 这句话是项目组成员事后向整理者复述的内容；不能作为任何一位具体受访者的“逐字原话”。“很多”“普遍”反映的是项目组成员的印象，**没有经过人数统计或独立验证**。

## 3. 与 ChangeScope 需求的初步联系

| 口头反馈 | 可能有用的候选功能 | 关联草案 | 证据边界 |
|---|---|---|---|
| 多人提交 PR 后难以统一检查 | 可见的 PR 变更列表、风险概览 | FR-05 / UC05、FR-07 / UC07 | 支持“审查和整合繁琐”这一问题线索，**尚不能证明风险评分有效** |
| 审查多个提交时可能难以定位重点 | 风险指标解释与审查重点提示 | FR-07 / UC07、FR-08 / UC08 | 属于解决方案假设，需让受访者评价 |
| 不确定其他文件是否受影响 | 历史关联文件提示 | FR-09 / UC09 | **本次回忆没有直接提到文件遗漏**，不能写成用户明确提出过 |
| 处理多人提交时审查协调困难 | 审查员推荐 | FR-14 / UC14 | **本次回忆没有提到审查员分配问题**，仍需独立验证 |

**两类问题与系统边界（更新）：**

- **PR审查繁琐：** 为 ChangeScope 的**核心问题域**。系统拟提供PR风险概览、历史关联文件证据、审查重点提示以及反馈追溯；其有效性仍待使用者核实与实验评估。
- **合并冲突：** 是**确实被回忆到的另一类痛点**，但当前 ChangeScope **不实现自动冲突解决**。候选扩展是基于 GitHub 状态的“PR可能存在合并冲突/不可直接合并”提示，并可跳转 GitHub 原生解决界面；其可行性、价值与API权限需单独评审。它不等同于历史共变更关系。
- **不应混淆：** 同一文件发生 Git merge conflict 属于分支合并的文本/内容冲突；“两个文件历史上一起修改”只是统计线索，两者不能相互替代。

## 5. 建议的真实性补强

1. 优先回访**原先交流过**的2—3位同学，不必再做整套正式访谈。
2. 发给对方这段事后整理的意思，询问“有没有说偏”。
3. 进一步询问：两种困难分别出现过什么实际场景？哪一种更频繁？合并冲突是哪些文件冲突，审查繁琐是哪些步骤繁琐？
4. 请对方分享**一个能够脱敏描述的真实经历**，不强制提供私人仓库地址。
5. 受访者确认后用 `IR-01` 等真实编号记**实际确认日期**、角色、回答摘要及证据链接；不能把确认日期冒充为当初访谈日期。
6. 如果回复与原先理解不一致，按回复修正 `OR-01/OR-02`，保留差异记录。

## 6. 课堂可采用的准确表述

> 我们在选题前和多名同学就 GitHub PR 协作做过非正式交流。由于当时没有按正式访谈留记录，今天展示的是**事后回忆整理**，不作为逐字访谈笔录。同学们反馈的主要方向是：多名组员共同开发时，PR 的合并和检查比较繁琐。我们由此提出了 PR 变更信息整理和风险分析的候选需求；两类问题都曾被提到，但各自的典型案例和频率仍需向原受访同学复核；我们的第一阶段重点放在审查辅助，不承诺自动解决合并冲突。我们已经把这个证据限制写进需求材料，没有将尚未验证的算法效果说成用户结论。
